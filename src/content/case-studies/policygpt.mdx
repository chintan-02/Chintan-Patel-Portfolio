## Problem

Policy answers can affect employee expectations, operational procedures, compliance reviews, and governance decisions.

A fluent answer is not enough. Reviewers need to know which document supports the response, which page contains the evidence, whether the retrieved text directly answers the question, whether numeric details are consistent, and what happens when the information is absent or the generation provider is unavailable.

Most basic PDF-chat systems retrieve several chunks and rely on an LLM to produce something plausible. PolicyGPT was built around a stricter principle:

> **Evidence must earn the right to generate an answer.**

## Product objective

The goal was to build a reviewable evidence workflow that could:

- establish durable document identity
- preserve page-level provenance
- prevent duplicate indexing
- separate metadata, source files, vectors, and evaluation artifacts
- evaluate answerability before generation
- block unsupported requests
- return page citations and confidence diagnostics
- remain useful when the optional LLM provider is unavailable
- expose benchmark and readiness states
- survive a safe Docker Compose stop-and-start cycle without losing persisted data

The intended portfolio use cases include HR and People Operations review, policy ownership, internal knowledge management, compliance review, SOP support, and retrieval-quality engineering. No real-company adoption is claimed.

## Core workflow

1. A user uploads a bounded PDF through the Next.js Documents workspace.
2. FastAPI validates the file and calculates a SHA-256 content hash.
3. PostgreSQL establishes document identity and prevents duplicate ingestion.
4. The source PDF is stored atomically under a generated storage key.
5. PyMuPDF extracts page-aware text.
6. Cleaning and chunking preserve document, page, section, and chunk metadata.
7. SentenceTransformer embeddings are generated locally.
8. Chunks and embeddings are persisted in ChromaDB.
9. The Next.js server-side BFF sends policy questions to FastAPI without exposing internal service configuration.
10. Retrieval produces candidate evidence.
11. The evidence layer evaluates retrieval strength, margin, lexical coverage, numeric consistency, direct support, and scope risk.
12. The evidence gate chooses generated answer, citation-only fallback, or unsupported state.
13. The response returns page-level evidence and inspectable confidence diagnostics.

The architecture separates four ownership responsibilities:

1. PostgreSQL owns document identity and lifecycle metadata.
2. Source storage owns original PDF files.

## Evidence gate and confidence design

PolicyGPT does not present vector similarity as the probability that an answer is correct.

The confidence value is an **answerability signal** informed by:

- top and average retrieval scores
- retrieval margin
- query-to-evidence lexical coverage
- top-chunk lexical coverage
- numeric consistency
- direct support
- scope or external-authority risk

The evidence gate operates before generation. If the documents do not directly support the request, the system does not ask an LLM to improvise.

Three truthful outcomes are possible:

- **supported evidence and provider available:** generate an answer with page-level citations
- **supported evidence and provider unavailable:** return citation-only evidence and identify the degraded provider state
- **unsupported evidence:** block generation and return a controlled unsupported response

This prevents a provider outage from being misrepresented as missing policy evidence and prevents weak retrieval from being presented as a supported answer.

The release-like local profile uses:

```text
PostgreSQL becomes healthy
→ Alembic migrations complete
→ FastAPI becomes ready
→ Next.js becomes ready
```

Named volumes persist PostgreSQL data, Chroma data, source PDFs, structured logs, and evaluation artifacts. Backend and frontend images run as non-root users.

Liveness confirms that the FastAPI process is running. Readiness checks the PostgreSQL and Chroma dependencies required for evidence workflows. The optional generation provider does not gate readiness because retrieval and citation review remain useful without it.

Every request receives a validated or generated request identifier that is returned in headers and included in normalized errors and structured completion logs. The application avoids logging document bytes, request bodies, questions, answers, credentials, cookies, chunks, or embeddings.

## Security boundaries

The release profile includes constrained CORS, fail-fast configuration, conservative security headers, normalized errors, disabled Next.js powered-by headers, and server-only upstream configuration.

Operational responses do not expose connection strings, credentials, provider keys, service hosts, storage paths, stack traces, raw chunks, or embeddings.

These controls improve the engineering baseline, but they are not a complete security model. Authentication, authorization, tenant isolation, malware scanning, managed secrets, TLS termination, formal retention policies, security certification, and production governance remain outside the current implementation.

## Engineering challenges and decisions

### Document identity before expensive processing

Duplicate detection needs to happen before extraction and embedding. PolicyGPT hashes the complete file and uses PostgreSQL uniqueness to prevent duplicate rows and vectors even when filenames change.

### Provenance without destroying page boundaries

PDF cleaning can remove useful citation structure. Processing remains page-aware so document, page, section, and chunk provenance survive cleaning and indexing.

### Answerability beyond vector similarity

Topical similarity does not guarantee direct support. The evidence layer adds lexical, numeric, direct-support, and scope-risk checks before generation.

### Provider resilience

An LLM outage should not hide valid policy evidence. Local embeddings and Chroma retrieval remain available, and supported evidence can be returned in citation-only form.

### Multiple persistence owners

PostgreSQL, source storage, Chroma, and evaluation artifacts have different responsibilities. Explicit ownership makes operational boundaries visible, though future backup and recovery must coordinate all stores.

### Synchronous ingestion

Synchronous ingestion keeps lifecycle state inspectable and easier to demonstrate, but it is not suitable for high-volume or long-running uploads.

## Current limitations

PolicyGPT Enterprise is not a finished production platform.

Current limitations include:

- no cloud deployment or real-company production usage
- no authentication, RBAC, or tenant isolation
- no malware scanning or object storage
- no managed secrets or TLS termination
- no formal retention or compliance certification
- synchronous ingestion
- single-instance embedded Chroma
- local source-file storage
- no document deletion or reindexing
- no background worker queue
- no managed backups
- no distributed tracing platform
- no hosted monitoring or alerting
- no multi-document comparison
- a controlled 16-case benchmark rather than broad domain validation

## Roadmap

The next production-oriented sequence is:

1. identity, authentication, authorization, and tenant boundaries
2. object storage, malware scanning, retention, deletion, and reindexing
3. asynchronous jobs, retries, dead-letter handling, progress, and cancellation
4. managed PostgreSQL, coordinated backups, distributed vectors, TLS, and secrets
5. OpenTelemetry, metrics dashboards, alerting, and provider cost monitoring
6. hybrid retrieval, reranking, document-scoped Ask, multi-document comparison, and a larger human-reviewed benchmark
7. controlled report and comparison workflows

Agentic orchestration should be considered only after identity, evaluation, observability, and recovery controls are established.
