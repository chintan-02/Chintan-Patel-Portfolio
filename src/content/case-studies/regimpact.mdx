## Problem

Regulatory change is not just a document-search problem.

A useful system must preserve evidence of **what changed**, show **which obligation was inferred**, identify **which internal controls may be affected**, record **who reviewed the proposal**, and preserve **why the final decision was accepted, rejected, deferred, or confirmed unmapped**.

RegImpact was therefore designed as an **analyst-assurance platform**, not a regulatory chatbot, legal-advice service, or autonomous compliance decision-maker.

A representative workflow is a regulator changing an incident-reporting deadline. RegImpact identifies the old and new clauses, retrieves the internal control that still reflects the previous deadline, cites both sources, and presents the impact proposal for review. The system does not silently modify the control.

PostgreSQL owns tenants, metadata, lineage, workflow state, and audit events. Blob Storage owns immutable source bytes. Search indexes and embeddings are treated as derived projections that can be rebuilt.

## Retrieval and decision design

The current release deliberately favors explainable, testable components for high-consequence decisions.

- PostgreSQL full-text search provides lexical retrieval.
- pgvector cosine similarity provides semantic retrieval.
- Reciprocal-rank fusion combines the two result sets.
- Results remain tenant-scoped and preserve citation and embedding-model lineage.
- Obligation candidates expose evidence and explainable confidence features.
- Control mappings preserve ranked candidates, ambiguity, unmapped states, and evaluation lineage.
- Low-confidence or policy-sensitive outcomes route to authorized human review.

The design principle is:

> **Models propose; policy gates constrain; authorized people decide.**

## Human review and governance

Human authority is not an optional UI layer. It is part of the workflow contract.

Review decisions support:

- accepted
- rejected
- deferred
- confirmed unmapped

Rationale is mandatory, stale-update protection prevents silently overwriting newer decisions, and creator/approver separation prevents one actor from unilaterally proposing and approving a consequential change.

## Security and reliability

The implemented security boundary includes:

- database-backed users with admin, analyst, and viewer roles
- scrypt password hashing
- short-lived signed tokens
- HTTP-only cookies
- tenant isolation
- server-validated actor and tenant identity
- controlled URL retrieval with SSRF-oriented protections
- signature-verified PDF/HTML intake and strict document limits
- non-development fail-closed malware-scanning boundary

The reliability model includes:

- transactional outbox
- Redis/Dramatiq workers
- idempotent jobs
- retries and leases
- dead-letter state
- startup, liveness, and readiness probes
- structured JSON logs
- request, trace, tenant, and actor correlation
- W3C trace context
- metrics, Application Insights, and Log Analytics

## Deployment lessons

The successful release was reached by fixing several independent Azure integration failures rather than treating deployment as one opaque event.

### Log Analytics retention

The original staging retention value was unsupported for the selected workspace contract. The configuration was aligned to the supported SKU and retention requirements.

### Key Vault purge protection

Azure does not allow purge protection to be reverted from enabled to disabled. Non-production deployment logic was changed to omit the property instead of trying to write `false`.

### OIDC token lifetime

A long infrastructure deployment exhausted the original Azure session before registry operations. The workflow now refreshes the Azure session immediately before ACR login.

### pgvector enablement

PostgreSQL Flexible Server requires the `VECTOR` extension to be allow-listed before Alembic can create pgvector objects.

### Two-phase promotion

Reapplying PostgreSQL configuration during workload promotion caused a `ServerIsBusy` collision. The two-phase deployment now applies extension configuration during the foundation phase only.

These fixes are encoded in infrastructure and workflow code, making the successful result repeatable rather than a one-off console procedure.

## Current limitations

RegImpact is not approved for production use.

Current production boundaries include:

- private networking still required
- enterprise malware scanning still required
- Entra workforce identity still required
- restore drills and broader recovery validation still required
- Azure Managed Redis remains a production consideration
- Kubernetes runtime validation is not yet complete
- fresh sanitized staging screenshots are still pending
- the future classifier is not yet a trained and promoted production model

These are deliberate boundaries, not hidden gaps.
