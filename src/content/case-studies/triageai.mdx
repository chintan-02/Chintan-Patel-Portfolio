## Try the workflow

Open the demo and choose **Start a private demo session**. Use synthetic information only. Extract a clinical note, correct the fields, confirm review, and run prediction. Accept or override the suggestion, then generate a PDF and inspect the audit trail. A new workspace starts empty. Sessions are temporary and the first API request can take longer during a cold start.

## Problem and my contribution

Emergency intake needs reviewable information, rather than just a model label. I built data preparation and registry integration, deterministic clinical-note extraction, the React/FastAPI workflow, safety rules, clinician review, persistence, PDF reporting, cloud delivery, and validation. This is educational decision support; it does not diagnose patients or claim clinical validation.

## Model evaluation and calibration

The source dataset contains 366,890 emergency-department records; the ESI 3/4/5 modelling subset contains 257,306. The runtime uses the final **273-feature LightGBM V2 registry**, a **0.60 threshold**, and raw model probabilities. ESI 1/2 escalation uses explicit safety rules outside this classifier.

Macro F1 gives each class equal weight. The lower **54.70% ESI 5 F1** remains a limitation even with 78.32% overall accuracy. The registry reports **70.37% macro F1**, **78.88% weighted F1**, and **215 ESI 3-to-5 downgrades (0.68% of true ESI 3 cases)**.

<ExpandableImage src="/images/case-studies/triageai/esi5-calibration.svg" alt="ESI 5 reliability curve: raw LightGBM predicted probabilities exceed observed class frequencies across most bins" label="ESI 5 reliability curve from the committed registry report" imageClassName="h-auto w-full rounded-panel bg-white" />

The curve shows that raw probabilities should not be read as calibrated clinical confidence. Calibration was evaluated: Platt scaling improved test Brier score from **0.312 to 0.281**, but the validation selection rejected it because macro F1 and ESI 5 F1 were not preserved. Isotonic calibration was also rejected because ESI 5 F1 was not preserved. This records a tradeoff; it does not establish that the deployed probabilities are calibrated.

[Final test metrics](https://github.com/chintan-02/triageai-esi-care-routing/blob/8af95ea72bfe595c4b0789ef352556d84e661bec/model_registry/esi_345_lightgbm_v2/reports/lightgbm_v2_test_metrics.json) · [Calibration decision](https://github.com/chintan-02/triageai-esi-care-routing/blob/8af95ea72bfe595c4b0789ef352556d84e661bec/model_registry/esi_345_lightgbm_v2/reports/calibration_deployment_decision.csv) · [Model-selection article](/writing/lightgbm-vs-xgboost)

## Architecture, review, and safety

<ExpandableImage src="/images/case-studies/triageai/13-system-architecture.png" alt="Reviewed intake flows through FastAPI, LightGBM, safety rules, clinician decision, database, audit trail, and PDF reporting" label="TriageAI system architecture" imageClassName="h-auto w-full bg-white" />

FastAPI and PostgreSQL own assessments, predictions, reviews, audit events, and official reports. The browser is not the source of truth. Reviewed extraction metadata preserves supported fields and evidence without storing raw note text in the NLP audit payload. The NLP layer does not infer diagnoses, treatments, or ESI decisions.

Database-backed sessions and owner-scoped APIs isolate demo workspaces. Backend tests check cross-workspace access and replace client-supplied reviewer identity with the authenticated principal. The Doctor demo role is a workflow permission, not verification of professional credentials.

## Cloud delivery and reliability

Netlify serves React; a non-root Cloud Run container serves FastAPI and the real registry. Neon PostgreSQL stores application data, while a private GCS bucket stores reports. Secret Manager supplies secrets. Separate runtime, migration, and cleanup database identities limit privileges; migrations run separately from startup.

<ExpandableImage src="/images/case-studies/triageai/cloud-deployment.svg" alt="Netlify, Cloud Run, Neon PostgreSQL, private GCS, Secret Manager, scheduled cleanup, and Cloud Monitoring" label="Educational cloud deployment topology" imageClassName="h-auto w-full bg-white" />

Release verification tested a private candidate before traffic promotion, with digest-pinned images and recorded rollback information. This was an operator-driven release, not automatic cloud CI/CD. Two uptime checks and five alert policies cover availability, API errors, and cleanup. A temporary alert verified opening and closure email delivery; not every failure condition was exercised.

Hourly cleanup targets eligible inactive workspaces older than 24 hours. Active-session exclusions and batch limits mean this is not an exact deletion deadline. Quotas and shared rate limits constrain demo usage.

## Validation and evidence

The documented release snapshot records **160 Python tests passed, one PostgreSQL-only case skipped locally, and 60 React tests passed across 15 files**. Production frontend build, Docker full-stack checks, health, and readiness passed. PostgreSQL migrations and API integration were checked separately in CI. These historical results are software verification, not a new test run or clinical validation.

## Limitations and next steps

No real-patient deployment, patient-outcome improvement, clinical validation, compliance certification, or uptime SLA is claimed. Staging and demo share database and report infrastructure. Independent staging, verified cloud database restoration, staff identity lifecycle, prospective clinical validation, and live drift monitoring remain future work. Offline subgroup reports exist; they do not replace clinical or prospective subgroup validation. Optional Azure Speech is not a verified live capability.

The next ML work is a reproducible baseline comparison against the final registry and broader evaluation of calibration, subgroup errors, and safety-rule behavior. The next operational work is isolated staging and a tested restore procedure.
